临界区 Critical Section

一个程序运行多个线程本身是没有问题的，问题出现在多个线程同时对共享资源的修改产生的指令交错，就会出现线程安全的问题，如果一段代码出现了对共享资源的读写操作这段代码块叫做临界区。多个线程在临界区执行，由于代码的执行顺序不同而导致结果没有办法进行预测，称之为竞态条件

为了避免这种竞态条件的发生，可以用到的手段有

阻塞式的解决方案：synchronized、Lock

非阻塞式的解决方案：原子变量

锁原理

Java对象头

对象头是构成Java对象的一部分， 对象的头部结构大致上会被分成三个部分分别是：对象头、实例数据、对齐填充。

普通对象头主要是由两部分组成：Mark Word （32 bits）和 Class Word（32bits）

数组对象头主要是由三部分组成：Mark Word （32 bits）和 Class Word（32bits）和 Array Length（32bits）。

**Mark Word：**它标识了一个对象在不同加锁状态下的一个结构。

**Klass Word：**简单理解成为指向该对象对应的方法区类对象的一个指针，通过这个指针就能够标识该类是那个类型的数据。

**Array Length：**数组独有，用来标识数组的长度。

Monitor

Monitor被叫做监视器，每一个java对象都可以关联一个monitor对象，如果使用synchronized给对象上锁之后，改对象头的Mark Word 中就被设置指向Monitor对象的指针。

Monitor的核心组成有如下几个：WaitSet、EntryList、Owner

**Owner：**当前持有Monitor对象的线程信息

**EntryList：**阻塞队列，因为在同一个时间只有一个线程能抢到锁，没有抢到锁的线程就会被阻塞，也就是加入到Monitor对象的EntryList中，等待Owner中的线程释放锁以后，在重新去争抢。

**WaitSet：**等待集合，当持有锁的线程调用了锁对象的wait方式时候，因为wait方法会去释放当前锁，所以当前的线程就会从Owner中退出然后加入到Wait中，并且状态变成waitting，等待其他的线程重新唤醒。

Monitor的工作流程

  • 最初Monitor里面的Owner是null
  • 当Thread-2执行 synchronized(obj) 就会将 Monitor 的所有者Owner置为Thread-2，Monitor中只能有一个 Owner，obj对象的Mark Word指向Monitor。
  • 再Thread-2持有锁的过程中，Thread-3、Thread-4、Thread-5线程来了以后，会进入阻塞队列EntryList BLOCKED
  • Thread-2线程执行完毕以后，释放Owner。
  • 唤醒EntryList中等待的线程来竞争锁，竞争是非公平的，如果这时有新的线程想要获取锁，可能直接就抢占到了，阻塞队列的线程就会继续阻塞。

Synchronzied优化

在JDK 1.6 对Synchronized进行了锁优化。

1、锁升级

锁升级的过程：无锁 -> 偏向锁 -> 轻量级锁 -> 重量级锁

偏向锁：锁会偏向于第一个获取它的线程，如果在下面的执行过程中，没有其他的线程来争抢这把锁，则持有偏向锁的线程将永远不需要再进行同步。如果其他的线程拿到了这把锁，偏向锁会升级成轻量级锁。

验证偏向锁是否生效

默认偏向锁生效是有延迟的，需要添加JVM参数来禁用延迟 -XX:BiasedLockingStartupDelay=0。

如果有大量的线程来争抢锁的话，偏向锁的效率反而会降低，此时使用偏向锁就不合适了，可以通过JVM参数来禁用偏向锁-XX:-UseBiasedLocking。

偏向锁撤销：

  • 调用对象的hashCode
  • 其他线程争抢
  • 调用wait/notify

批量撤销：如果对象被多个线程访问，但没有竞争，这时偏向了线程T1的对象仍有机会重新偏向T2，重偏向会重置对象的Thread ID

  • 批量重偏向：当撤销偏向锁阈值超过 20 次后，JVM 会觉得是不是偏向错了，于是在给这些对象加锁时重新偏向至加锁线程
  • 批量撤销：当撤销偏向锁阈值超过40次后，JVM 会觉得自己确实偏向错了，根本就不该偏向，于是整个类的所有对象都会变为不可偏向的，新建的对象也是不可偏向的

轻量级锁：两个线程之间不存在竞争关系，这个时候使用轻量级锁，也就是说多个线程错开访问。

加锁流程

  • 线程进入Synchronized代码块，JVM会先查看加锁对象的的状态，对象头里有一块叫 Mark Word，里面会存锁标志位、哈希码、GC 年龄等信息。
  • 在线程栈中开辟一个 Lock Record所记录
  • 用CAS尝试替换掉对象头

原始值：锁对象原来的Mark Word

新值：指向当前线程Lock Record的指针，并把锁标志改成轻量级锁状态

CAS成功，证明当前线程获得到了这把轻量级锁

  • CAS失败，CAS失败不一定是有多线程竟争抢，还需要分成下面的两种情况

  • 当前线程发生锁重入

如果是线程自己执行了synchronized锁重入，就添加一条Lock Record作为重入的计数

解锁，如果有取值为null的锁记录，表示有重入，这时重置锁记录，表示重入计数减1，如果锁记录的值不为 null，这时使用CAS将Mark Word的值恢复给对象头，此时则解锁成功。

解锁失败进入重量级锁的解锁流程

  • 多线程竞争

如果对象头不是指向当前线程的锁记录，说明别的线程也在抢这把锁。这时候轻量级锁的“无阻塞”优势就不够了，JVM 通常会先做一段自旋；如果竞争持续，锁就会膨胀（inflate）成重量级锁，底层走Monitor机制，线程可能会阻塞挂起。

实例代码

重量级锁：轻量级锁存在竞争会升级到重量级锁，两个线程之间存在相互竞争的关系

当Thread-1进行轻量级加锁时，Thread-0已经对该对象加了轻量级锁

Thread-1加轻量级锁失败，进入锁膨胀流程：为Object对象申请Monitor锁，通过Object对象头获取到持锁线程，将Monitor的Owner置为Thread-0，将 Object 的对象头指向重量级锁地址，然后Thread-1进入 Monitor 的 EntryList BLOCKED

当Thread-0退出同步块解锁时，使用CAS将Mark Word的值恢复给对象头失败，这时进入重量级解锁流程，即按照Monitor地址找到Monitor对象，设置Owner为null，唤醒EntryList中BLOCKED线程

2、锁粗化

扩大锁的范围，避免重复的加锁释放锁

首先不考虑优化器的问题，如果在 for 循环中定义锁，那么锁的范围很小，但每次 for 循环都需要进行加锁和释放锁的操作，性能是很低的；但如果我们直接在 for 循环的外层加一把锁，那么对于同一个对象操作这段代码的性能就会提高很多。

锁粗化的作用：如果检测到同一个对象执行了连续的加锁和解锁的操作，则会将这一系列操作合并成一个更大的锁，从而提升程序的执行效率。

3、锁消除

JVM 虚拟机如果检测不到某段代码被共享和竞争的可能性，就会将这段代码所属的同步锁消除掉，我是这样理解的，就是不会从方法中发生逃逸的变量。

4、自旋锁

轻量级锁CAS失败，避免这个线程被放到这个阻塞队列，因为占有资源的哪个线程有可能在很短的时间内释放资源，如果让抢锁的哪个线程放入到阻塞队列，到时候又得重新唤醒，这样的线程之间的切换非常不值得。这个时候会进行一个循环的操作，等待锁释放，不让出cpu，拿到锁以后进入到临界区。如果一直不能获取到锁，那么线程就会在操作系统挂起来。存在的问题，自选的方式虽然避免了线程之间的一个切换开销，但是如果锁长时间被占用，那么自选会白白的浪费消耗自己的处理器资源。

5、自适应自旋

由于自选锁带来的问题在JDK1.6引入了自适应自选，

自适应意味着自旋时间不再固定，而是由前一次在同一个锁上的自旋时间及锁的拥有者状态决定。如果在同一锁对象上，自旋等待刚刚成功获得过锁，那么虚拟机认为这次自旋也很有可能再次成功，进而允许线程自旋更长时间，例如自旋 100 个循环。

但如果对于某个锁，自旋很少成功获得过。那虚拟机为了避免浪费 CPU 资源，有可能省略掉自旋过程。有了自旋锁，随着程序运行和性能监控信息的不断完善，虚拟机对锁的状态预测就越准，虚拟机也会变得越来越聪明。

Wait / Notify

需要获取对象锁以后才可以调用wait方法，notify随机唤醒一个线程，notifyAll唤醒所有的线程去竞争CPU

api

wait/notify原理

  • Owner 线程发现条件不满足，调用wait方法，即可进入WaitSet变为WAITING状态
  • BLOCKED 和 WAITING 的线程都处于阻塞状态，不占用 CPU 时间片
  • BLOCKED 线程会在 Owner 线程释放锁时唤醒
  • WAITING 线程会在 Owner 线程调用 notify 或 notifyAll 时唤醒，唤醒后并不意味者立刻获得锁，需要进入 EntryList 重新竞争

sleep 和 Wait的区别

1、sleep是Thread的方法，Wait是Object的方法

2、sleep不需要配合synchronized使用，但是wait需要配合

3、sleep在睡眠的同时，不会释放对象锁的，但是wait在等待的时候会释放对象锁。

wait / notify 会产生虚假唤醒的问题，可以使用notifyAll唤醒全部的正在waitset中等待的线程。这种方式可以解决虚假唤醒问题，但是显然不是最优的方式。

锁的活跃性

死锁

死锁是所有的线程都暂停了，并且线程之间相互等待。

场景举例

  • 线程A拿着锁L1，等待锁L2
  • 线程B拿者锁L2，等待锁L1

结果就是

  • 线程A不释放L1，因为它还在等待L2
  • 线程B不释放L2，因为它还在等待L1

所以导致这两个线程谁都走不下去

就好像两个人各自拿者一把钥匙，但是都再等对方开门，最终导致的结果就是谁都进不去。

死锁的产生通常需要满足4个条件：互斥、请求并保持、不可剥夺、循环等待。

解决办法

  • 统一加锁顺序，比如都先拿 L1 再拿 L2
  • 尽量避免同时持有多个锁
  • 使用超时锁、tryLock
  • 减少锁粒度

活锁

活锁是“线程都没卡住，都在执行，但谁也没真正完成工作”。

场景举例

  • 线程 A 发现线程 B 在争资源，于是主动退一步
  • 线程 B 也很礼貌，也退一步
  • 两边不断让来让去，结果谁都没完成任务

生活类比

  • 两个人在狭窄走廊迎面相遇
  • A 往左让，B 也往左让
  • 然后两人又同时往右让
  • 一直在动，但就是过不去

活锁的特点是

  • 线程不是阻塞的，而是在不断重试、回退、重来
  • 看起来很忙，CPU甚至可能很活跃
  • 但程序没有实质进展

解决办法

  • 引入随机等待时间，避免双方总是同步重试
  • 设定优先级，让一方先走

饥饿

饥饿是“系统整体在运行，但某个线程一直拿不到它需要的资源，所以长期得不到执行”。

场景举例

  • 低优先级线程争抢不过高优先级的线程
  • 某个线程一直乖乖的排队，但是资源总是被其他线程拿走

生活类比

  • 就好比食堂打饭，食堂一直再发饭，但是每次块轮到你是，总有人插队插到你的前面，食堂并没有停止发饭，但是你就是吃不上饭

饥饿的特点

  • 系统整体是正常运转的，只是某些线程长期得不到执行的机会，线程没有卡死，但是有可能会等待很久。

解决办法

  • 使用公平锁
  • 调整线程的优先级
  • 让等待时间久的线程提升优先级

ReentrantLock

ReentranLock是一把可重入的锁，相较于synchronized它的功能更多一点。

他有一下的特点，可以中断、可以设置超时时间、可以设置为公平锁、还支持多个条件变量。

基本的语法

可重入

可重入是指同一个线程如果首次获得了这把锁，那么因为它是这把锁的拥有者，因此还有权力获得这把锁。

不可重入，在第二次获取锁的时候，自己也会被锁挡住

锁超时

避免一直等待，防止死锁。

可打断

可打断需要使用lockInterruptibly进行加锁

自定义公平锁和非公平锁

ReentrantLock默认非公平，ReentrantLock lock = new ReentrantLock(true); 可以设置为公平锁，公平锁会降低并发度，因此推荐使用非公平锁。

非公平锁：不会按照进入阻塞队列的顺序进行执行，谁先抢到就算谁的。

公平锁：会按照抢到锁的顺序进行执行。
